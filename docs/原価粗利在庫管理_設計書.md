# HIIRAGI 原価・粗利・在庫管理機能 設計書

作成日: 2026年5月22日
対象アプリ: HIIRAGI（整備工場向けマルチテナントSaaS）
想定ブランチ: feat/cost-and-inventory
前提: 作業メニュー・作業セット・業務カテゴリ機能（feat/item-templates）が本番稼働済み

---

## 1. この機能で実現したいこと

整備工場（特にサスペンション修理）の経営判断に使える、原価・粗利の見える化と部品在庫管理を実装する。

- 作業ごと・受注ごとの粗利が見える
- 月次・年次の粗利レポートが見える
- 部品の原価（仕入値）を一元管理し、1箇所変えれば今後の見積に反映される
- 部品の在庫を管理し、なくなる前に発注できる
- 間接材料（Oリング等、明細に出さないが使う部品）も在庫管理できる

---

## 2. 確定した設計判断

| 項目 | 決定内容 |
|------|---------|
| マスター構造 | 設計Z系：作業メニューを主役に、部品マスター（在庫表）を追加 |
| 工賃マスター | 作らない。工賃は作業メニューに直接入力 |
| 原価の扱い | 工賃も部品も「原価」という枠でシンプルに（工数計算はしない） |
| 明細表示フラグ | 部品マスターに「明細に出す/出さない」フラグ。間接材料に対応 |
| 価格の確定 | 確定スナップショット方式（見積OK・請求済みは価格固定） |
| 間接材料の使用量 | メニューに標準使用量を登録（方法B） |
| 在庫を減らすタイミング | 受注確定時 |
| 在庫の減らし方 | シンプル版：確定時に実在庫を直接減らす（引当2段階はやらない） |

## 3. 中心となる考え方

### 3-1. 直接部品と間接材料

| 種類 | 例 | 明細に出す | 在庫管理 | 原価の行き先 |
|------|-----|-----------|---------|------------|
| 直接部品 | タイヤ、オイル | する | する | 部品代の原価 |
| 間接材料 | Oリング、グリス | しない | する | 工賃原価に算入 |

間接材料は「使うけど明細には個別に書かない部品」。お客さんへの請求は工賃に溶け込む。
ただし在庫管理（発注のため）と原価算入（粗利計算のため）はする。

### 3-2. 粗利の計算式

```
粗利 = 売上 − 原価

売上 = 工賃（売価） + 部品代（売価、明細に出す部品のみ）

原価 = 工賃原価 + 直接部品の原価 + 間接材料の原価
       （工賃原価には技術料 + 間接材料代が含まれる考え方）
```

### 3-3. 確定スナップショット方式（一元管理と過去保護の両立）

```
【見積・作業中】= マスター参照（最新価格をリアルタイム取得）
       ↓ ステータスが「確定」になる瞬間
【確定・請求済み】= その時点の価格を明細に焼き付け（以後マスターを変えても不変）
```

- マスターの価格を変えると、これから作る見積・作業中の受注に反映（一元管理）
- 確定済み・請求済みの受注は当時の価格で固定（過去保護・集計の整合）

## 4. データモデル案

### 4-1. 新規テーブル: parts_inventory（部品マスター／在庫表）

| カラム | 型 | 説明 |
|--------|-----|------|
| id | uuid | 主キー |
| user_id | uuid | テナント分離（RLS） |
| name | text | 部品名（例: Hirokoオイル 4L、Oリングφ20） |
| cost_price | numeric | 原価（仕入値） |
| sale_price | numeric | 売価（明細に出さない部品はnull可） |
| show_in_detail | boolean | 明細に出す=true / 間接材料=false |
| stock_quantity | numeric | 現在の在庫数 |
| reorder_point | numeric | 発注点（この数を切ったらアラート） |
| supplier | text | 仕入先（任意） |
| unit | text | 単位（個、本、L など、任意） |
| memo | text | メモ（任意） |
| display_order | integer | 表示順 |
| deleted_at | timestamptz | ソフトデリート |
| created_at / updated_at | timestamptz | |

### 4-2. 作業メニュー（work_menu_items）への追加カラム

| カラム | 型 | 説明 |
|--------|-----|------|
| labor_cost_price | numeric | 工賃の原価 |
| parts_cost_price | numeric | 部品代の原価（明細に出す部品） |
| linked_part_id | uuid | 部品マスターへのリンク（任意、null可） |

### 4-3. 新規テーブル: work_menu_indirect_materials（メニューの標準間接材料）

メニューごとに「標準で使う間接材料と数量」を登録。

| カラム | 型 | 説明 |
|--------|-----|------|
| id | uuid | 主キー |
| menu_item_id | uuid | どの作業メニューか |
| part_id | uuid | parts_inventory への参照 |
| quantity | numeric | 標準使用量（例: Oリング2個） |

### 4-4. 受注明細（orders.items jsonb）への追加フィールド

| フィールド | 説明 |
|-----------|------|
| labor_cost_price | 工賃原価（確定時にスナップショット） |
| parts_cost_price | 部品代原価（確定時にスナップショット） |
| linked_part_id | リンクした部品マスターID（在庫増減の対象特定用） |
| indirect_materials | この明細で使った間接材料のリスト（part_id, quantity, cost のスナップショット） |

### 4-5. 新規テーブル: stock_movements（在庫移動履歴）

入庫・出庫・棚卸し調整の記録。

| カラム | 型 | 説明 |
|--------|-----|------|
| id | uuid | 主キー |
| user_id | uuid | テナント分離 |
| part_id | uuid | parts_inventory への参照 |
| movement_type | text | 'in'（入庫）/ 'out'（出庫）/ 'adjust'（棚卸調整） |
| quantity | numeric | 増減数（+/-） |
| related_order_id | uuid | 関連受注（出庫時、任意） |
| unit_cost | numeric | その時の単価（入庫時の仕入値記録など） |
| memo | text | メモ |
| created_at | timestamptz | |

## 6. 段階的な実装計画（案）

大きな機能のため、昨日の作業メニュー機能と同様にステップを分割して進める。
各ステップで動作確認・コミット・ユーザー承認を挟む。

### Step 1: 原価フィールドと粗利計算（土台）
- 作業メニューに工賃原価・部品代原価を追加
- 受注明細に原価フィールドを追加（確定時スナップショット）
- 受注ごとの粗利を社内管理用に表示
- まだ部品マスター・在庫はやらない（コピー方式のまま原価だけ）

### Step 2: 部品マスター（在庫表）の新設
- parts_inventory テーブル作成
- 部品マスター管理画面（CRUD、在庫数、発注点、明細表示フラグ）
- 入庫登録、発注アラート表示

### Step 3: 作業メニューと部品マスターのリンク
- 作業メニューの部品を部品マスターにリンクできる
- リンクした部品は原価・売価をマスターから取得

### Step 4: 在庫の自動増減（受注確定時）
- 受注確定時に、リンクした部品の在庫を減らす
- ステータス管理（作業/見積/請求）との連動

### Step 5: 間接材料
- メニューに標準間接材料を登録（work_menu_indirect_materials）
- 受注確定時に間接材料の在庫も減らす
- 間接材料の原価を工賃原価に算入

### Step 6: 月次・年次の粗利レポート
- 売上・原価・粗利・粗利率の集計
- カテゴリ別粗利

### Step 7: 棚卸し・在庫履歴（任意）
- stock_movements の履歴表示
- 棚卸し調整機能

---

## 7. 未決事項・運用しながら決めること

- 工賃原価の精密化（標準作業時間×時間コスト方式）は将来検討。今は原価を直接入力
- 引当→出庫の2段階在庫管理は今回やらない。確定時に直接減らす
- 在庫を減らす「確定」が、HIIRAGIのどのステータス遷移に対応するか（実装時に詰める）
- 部品マスターを使わず手入力した部品の扱い（リンク任意のため、原価が2箇所に存在しうる点の運用）

---

## 8. 重要な原則（昨日の開発から引き継ぐ）

1. 既存機能・既存データを壊さない（特に過去の受注・PDF・集計）
2. 各ステップで動作確認してから次へ
3. 開発DBで完成・確認してから本番DBにマイグレーション
4. 過渡期は新旧フィールドを並走させ、段階的に切り替える
5. 一度に全部作らず、土台から順に積む
